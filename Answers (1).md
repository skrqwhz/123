# Лекция 2. Сеть, трафик и firewall — ответы на вопросы для размышления

## 1. SSH на `127.0.0.1:22` при открытом порте 22 в firewall

Снаружи по SSH никто не подключится. Пакет на `203.0.113.10:22` пройдёт INPUT, потому что правило `ACCEPT dpt:22` его пропустит. Но на этом адресе никто не слушает: сокет привязан только к `127.0.0.1`. Ядро ответит `RST` (connection refused).

«Главнее» тот, кто строже. Firewall решает, пустить ли пакет к машине, а привязка решает, есть ли кому его принять. Для доступа нужны оба условия.

Правило `ACCEPT` здесь опасно: стоит кому-то сменить `ListenAddress` на `0.0.0.0`, и SSH сразу окажется открыт всему интернету.

## 2. Чего не хватает `web42ns` для выхода в интернет

- **Маршрут по умолчанию внутри namespace.** Без него namespace не знает, куда слать пакеты не из `10.200.0.0/24`:

  ```
  sudo ip netns exec web42ns ip route add default via 10.200.0.1
  ```

- **Пересылка пакетов на хосте.** Хост должен работать как роутер:

  ```
  sudo sysctl -w net.ipv4.ip_forward=1
  ```

  Если политика цепочки FORWARD равна DROP, нужно дополнительно разрешить этот трафик.

- **`MASQUERADE` в POSTROUTING** для подсети `10.200.0.0/24` на выходе через `eth0`:

  ```
  sudo iptables -t nat -A POSTROUTING -s 10.200.0.0/24 -o eth0 -j MASQUERADE
  ```

**Роль `MASQUERADE`.** Адрес `10.200.0.2` приватный и в интернете не маршрутизируется. Если пакет уйдёт с таким источником, его отбросят по дороге, а даже если он дойдёт до адресата, ответ вернуться не сможет. `MASQUERADE` подменяет источник на внешний адрес `203.0.113.10`. Хост запоминает это соответствие и при возврате ответа переписывает адрес обратно на `10.200.0.2`.

## 3. Почему трафик к `web-42` не отсекается ни INPUT, ни ufw

Пакет на `203.0.113.10:8080` сначала попадает в **PREROUTING**. Там Docker-овский DNAT переписывает адрес назначения на `172.17.0.2:8080`. Это происходит **до** выбора маршрута. Когда ядро решает «это мне?», адрес уже не локальный, а принадлежит подсети `docker0`. Поэтому пакет идёт транзитом в **FORWARD**, а не в INPUT.

- Отсутствие порта 8080 в INPUT ничего не значит, потому что INPUT этот пакет не видит.
- `ufw deny 8080` в основном правит INPUT, поэтому тоже не срабатывает.
- В FORWARD у Docker есть собственные разрешающие правила, и пакет проходит.

## 4. Сравнение: (а) открыть 8080 напрямую и (б) отдавать через nginx на 80

В варианте (а) «сайт вроде работает», но:

- **Нет TLS-терминации.** Каждое приложение должно само заниматься сертификатами, централизованно получать Let's Encrypt не выйдет.
- **Нет роутинга по домену.** Каждому сервису нужен свой порт, пользователям придётся писать `:8080` в адресе, а 80 и 443 нельзя разделить между сервисами.
- **Нет балансировки** нагрузки между копиями приложения.
- **Больше поверхность атаки.** Приложение торчит наружу напрямую, и на каждый новый сервис открывается ещё один порт.

Кроме того, нестандартные порты часто блокируются корпоративными firewall'ами.

В варианте (б) наружу открыты только 80/443, а внутренние сервисы спрятаны за reverse proxy.
